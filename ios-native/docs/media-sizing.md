# 媒体尺寸：现在怎么做，将来怎么改

**状态** 现状已实现；后端方案**仅为记录，本轮不动 `functions/src`、规则或生产数据**。

## 问题

`MediaItem` 只有 `{ url, type, thumbUrl? }` —— **没有宽高**。客户端在图片字节
到达之前无法知道它是什么形状，而验收 §6.4 要求"图片到位不引起布局跳动"。

两者不能同时满足：要么先留一个高度（可能与图片不符，于是要裁切），
要么等图片到了再决定高度（于是会跳动）。

## 现在的做法

**固定框 + 明确的裁切策略 + 完整图可达。**

| 决定 | 值 | 为什么 |
| --- | --- | --- |
| 默认比例 | **4:5**（竖幅） | 宠物照片以竖幅居多；关键是它**稳定**，不会因为图片到达而变 |
| 允许范围 | **4:5 – 16:9** | 超出的图按 `scaledToFill` 填满并裁切，不让一条帖子占满整屏 |
| 比例来源 | URL 里的 `ar_` **仅作提示** | 见下 |
| 被裁时 | 卡片下方显示"点图看完整"，详情页点图打开全图查看器 | 裁切是压缩显示，不是丢失内容 |

**`ar_` 不是尺寸依据，只是可用时的提示。** 我们的种子数据用 `ar_` 构造了多种
比例，生产 URL 则通常是 `upload/v123/id.jpg`，没有任何形状信息。所以代码把
`ar_` 当作"有就用、没有就回落到默认"，而不是当作可依赖的元数据——
`MediaView.frame(for:)` 返回 `MediaFrame { ratio, isCropped, declaredRatio }`，
`isCropped` 正是"这个框不是图片本来的形状"，UI 据此提示。

完整图片入口：详情页点图 → `FullImageView`（捏合缩放、拖动、双击、点 X 关闭）。
**不是图库**：同一帖多图之间翻页、分享、保存都还没做。

## 将来：在 MediaItem 里带上 width / height

以下是方案记录，**没有实施**。任何一步都要先获批，因为它们都会碰
`functions/src/**`、规则或既有数据。

### 尺寸从哪里来

Cloudinary 的上传响应本身就返回 `width` / `height`（以及 `format`、
`bytes`、`resource_type`）。现在 `createPostCallable` 拿到的是客户端给的
`media: MediaItem[]`，其中只保留了 url/type/thumbUrl。

两条路：

| 来源 | 优点 | 代价 |
| --- | --- | --- |
| **客户端上传后把 Cloudinary 响应里的宽高一并提交** | 不需要额外网络往返 | 是客户端报的数，服务端必须校验，否则等于信任客户端 |
| **服务端用 Admin API 按 public_id 回查** | 权威 | 每次发帖多一次外部调用，增加失败模式与延迟 |

建议**客户端提交 + 服务端校验**：发帖本来就已经在校验媒体 URL 属于我们的
cloud（曾出现过 `Media URL must point at an asset uploaded through PetNote.`
的守卫），在同一处顺带校验尺寸最省事。

### 方向旋转后"宽高"指什么

必须定义清楚，否则竖拍的照片会被记成横的：

- 存**显示尺寸**（即 EXIF 方向应用之后的宽高），不是传感器原始尺寸。
- Cloudinary 的 upload 响应在 `f_auto`/自动方向处理下返回的已是显示尺寸；
  如果将来关闭自动方向，这条要重新确认。
- 客户端解码时也应用方向（`kCGImageSourceCreateThumbnailWithTransform: true`，
  当前已这样做），两边才一致。

### 服务端校验

- `width`/`height` 必须是正整数，且上限合理（例如 ≤ 20000，挡住脏数据）。
- 比例必须落在可接受范围内，否则拒绝或钳制——决定权在产品，不是客户端。
- 与 URL 里可能存在的 `ar_`/`w_`/`h_` 变换**不必一致**：变换是渲染参数，
  宽高是原图属性。不要用一个校验另一个。

### 旧文档缺字段怎么办

- 客户端必须把缺失当作**正常情况**，不是错误：`width`/`height` 为可选，
  缺失时走现在这套默认框 + 裁切 + 可看全图。这条不能省，因为历史帖子永远存在。
- 解码层（`PostDecoder`）已经对每个字段做容错，加字段只是多两个可选值。

### 要不要回填

**建议不回填。**

- 回填需要对所有历史帖子逐条调 Cloudinary Admin API 拿尺寸再写回 Firestore，
  是一次大规模写入，风险与成本都不小。
- 收益随时间自然衰减：新帖子有尺寸，旧帖子越滚越远。
- 若将来确实要做，应作为独立工作项单独评估，并且**不得**由客户端触发。

### 客户端要改什么

很小：`PostDecoder` 多读两个可选字段，`MediaView.frame(for:)` 优先用真实宽高、
其次 `ar_`、最后默认值。裁切策略与全图入口都不必改——
它们对"不知道尺寸"这件事本来就是安全的。
